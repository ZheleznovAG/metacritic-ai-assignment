# Инженерная методология выполнения тестового задания

## 1. Цель и рамка

Это задание следует выполнять как разработку небольшого production-like data/AI-сервиса, но без избыточного production-hardening.

В задании одновременно проверяются:

- работа с ненадёжным внешним источником;
- почасовая и календарная логика обработки;
- безопасное повторное обновление данных;
- качество AI-результатов;
- пользовательские сценарии;
- эксплуатационная готовность;
- способность довести результат до публично доступного сервиса;
- прозрачное использование AI в процессе разработки.

Методология определяет **процесс работы, контрольные точки, критерии приёмки и инженерные практики**. Она намеренно не фиксирует стек, архитектуру, схему БД, API и конкретные алгоритмы.

Главный критерий успеха — не количество технологий и не максимальная полнота production-практик, а доказуемая цепочка:

> однозначные требования → проверенные внешние риски → работающий сквозной сценарий → безопасные повторы и сбои → проверенное качество AI → публичный воспроизводимый результат

---

## 2. Основные принципы

Для этого задания нужен короткий риск-ориентированный итеративный процесс.

1. Сначала формализовать требования и неоднозначности.
2. До основной разработки проверить самые опасные внешние допущения.
3. Двигаться вертикальными, демонстрируемыми инкрементами.
4. Сначала полностью закрыть обязательную часть, затем дополнительные.
5. Проверять не объём кода, а ключевые свойства системы и доказательства их выполнения.
6. Первую рабочую публичную версию развернуть рано.
7. С первого дня сохранять историю AI-assisted разработки.
8. Каждое исследование и необязательное улучшение ограничивать по времени.
9. Не выполнять инженерную работу, если она не связана с требованием, существенным риском или критерием приёмки.
10. При дефиците времени сокращать глубину необязательных практик, но не сквозной обязательный сценарий.

---

## 3. Уровни обязательности

Чтобы методология не превращалась в максималистский production-процесс, все практики делятся на три уровня.

### Must

Практики, без которых нельзя доказать выполнение задания или надёжно выполнить его обязательную часть.

### Should

Практики, существенно повышающие качество результата и желательные при нормальном бюджете времени.

### Optional

Улучшения, которые выполняются только после полного закрытия обязательной части.

Если практика не связана с критерием приёмки или существенным риском, она не должна вытеснять работу над обязательным контуром.

---

## 4. Формализация требований до разработки

Первым рабочим артефактом должна стать матрица трассировки требований.

Для каждого пункта задания фиксируются:

- приоритет: обязательная или дополнительная часть;
- трактовка требования;
- критерий приёмки;
- способ проверки;
- evidence — конкретное доказательство выполнения;
- текущий статус;
- известные ограничения.

Рекомендуемый формат:

| Требование | Приоритет | Трактовка | Критерий приёмки | Проверка | Evidence | Статус |
|---|---|---|---|---|---|---|

Evidence может быть:

- имя автоматического теста;
- ссылка на публичный сценарий;
- лог конкретного запуска;
- скриншот;
- метрика;
- шаг демонстрации;
- ссылка на commit или CI-run.

### Неоднозначности, которые нужно разрешить письменно

До реализации следует определить:

- какая временная зона определяет «сегодня» и начало нового дня;
- что считается лимитом 20: найденные, начатые или успешно обработанные игры;
- что происходит с игрой, обработка которой началась, но завершилась ошибкой;
- как однозначно определяется, что игра уже есть в базе;
- считается ли одна игра на разных платформах одной игрой с несколькими платформенными оценками;
- что обновляется при повторном обходе;
- как обрабатываются отсутствующие Metascore, Userscore, отзывы, видео и другие поля;
- какая оценка участвует в сортировке, если платформ несколько;
- сколько отзывов достаточно для AI-резюме;
- что показывается при недостатке отзывов;
- на каком языке должны быть AI-резюме;
- по каким проверяемым признакам игра считается похожей;
- что означает «самый популярный летсплей»;
- какая AI-переписка передаётся в составе результата.

Если уточнить требования у заказчика невозможно, принимается разумное допущение. Оно фиксируется в документации и последовательно применяется в реализации и тестах.

---

## 5. Минимальные критерии приёмки обязательной части

Матрица требований должна как минимум покрывать следующие сценарии.

| Область | Проверяемое поведение |
|---|---|
| Первый запуск дня | Берутся первые 20 игр из New Releases, которые ещё не обрабатывались в текущем дневном цикле |
| Последующие запуски | Берутся очередные ещё не обработанные сегодня игры из SEE ALL с сортировкой по новым |
| Новый день | Дневной цикл начинается заново с New Releases |
| Повторная встреча игры | Существующая запись обновляется без создания дубля |
| Несколько платформ | Для каждой платформы хранится и отображается соответствующая пара Metascore / Userscore |
| Отзывы | Резюме критиков и пользователей формируются и обновляются раздельно |
| Список | Пользователь видит краткую информацию о загруженных играх |
| Карточка | Пользователь видит все обязательные данные и ссылки |
| Навигация | Поиск, фильтр по платформе и сортировка дают ожидаемый результат |
| Похожие игры | Показываются только игры из собственной базы, без ссылки на саму себя |
| Эксплуатация | Почасовая обработка фактически выполняется после развёртывания |
| Сдача | Доступны репозиторий, публичный сервис и история работы с AI |

## 6. Timeboxing и управление объёмом

Это тестовое задание, поэтому инженерная глубина должна быть контролируемой.

Для каждого исследования и значимого улучшения до начала работы фиксируются:

- вопрос, на который нужно ответить;
- максимальный бюджет времени;
- достаточное доказательство;
- решение после завершения.

Работа прекращается, как только получено достаточное доказательство.

Дополнительная часть не начинается, пока обязательная часть не соответствует Definition of Done.

При дефиците времени приоритет сокращения такой:

1. дополнительные функции;
2. дополнительные метрики и автоматизация;
3. расширенные eval-наборы;
4. необязательные hardening-практики.

Не сокращаются:

- корректность обязательных сценариев;
- идемпотентность;
- дневная логика;
- восстановление после сбоев;
- базовая проверка AI-качества;
- публичный деплой;
- доказательства выполнения требований.

## 7. Короткие исследования главных рисков

До основной реализации проводятся ограниченные по времени technical spikes.

Цель spike — не написать часть будущего решения, а подтвердить реализуемость требования и снять ключевую неизвестность.

Каждый spike должен завершаться одним из решений:

- **Proceed** — риск подтверждён как приемлемый;
- **Proceed with limitation** — реализация возможна с явно документированным ограничением;
- **Drop optional scope** — необязательная часть отбрасывается;
- **Escalate assumption** — без дополнительного допущения двигаться дальше нельзя.

Для каждого spike фиксируются:

- вопрос;
- доказательство;
- вывод;
- оставшийся риск;
- принятое допущение;
- итоговое решение.

После spike обновляются матрица требований и реестр рисков.

### 7.1. Metacritic — Must

На репрезентативной выборке необходимо проверить:

- доступность обеих требуемых страниц локально и в среде развёртывания;
- фактическое поведение New Releases;
- сортировку и пагинацию SEE ALL;
- наличие и представление всех обязательных полей;
- варианты страниц с несколькими платформами;
- страницы с отсутствующими оценками, отзывами, изображением или видео;
- динамическую загрузку;
- сетевые ограничения и антибот-защиту;
- признаки разметки, изменение которых критично для извлечения;
- разумные ограничения частоты запросов и условия работы с источником.

Следует сохранить небольшой набор репрезентативных HTML-фикстур для воспроизводимых тестов.

Если фикстуры очищаются или сокращаются, это не должно менять структурно значимую разметку, которую проверяет parser contract.

Обычный CI не должен зависеть от постоянной доступности живого сайта.

### 7.2. AI-суммаризация — Must

На небольшой вручную проверенной выборке отзывов нужно подтвердить, что модель:

- не смешивает отзывы критиков и пользователей;
- выделяет положительные и отрицательные аспекты;
- не добавляет утверждения, отсутствующие во входных данных;
- корректно сообщает о недостатке данных;
- укладывается в приемлемые ограничения по времени и стоимости;
- возвращает результат в стабильном формате, пригодном для проверки и отображения.

Результатом spike становится:

- initial evaluation set;
- рубрика качества;
- baseline;
- минимальный критерий прохождения.

Конкретное числовое значение порога не обязано задаваться методологией заранее, но должно быть зафиксировано **до** оценки финальной реализации.

### 7.3. Публичное окружение — Must

Ранний spike должен подтвердить, что выбранная площадка поддерживает:

- публичный веб-сервис;
- устойчивое хранение состояния;
- почасовую фоновую работу;
- конфигурацию секретов;
- базовую диагностику.

Требование «работает локально» недостаточно.

### 7.4. YouTube — Optional

Перед дополнительной частью 1 нужен отдельный feasibility gate.

Проверяется:

- можно ли достаточно надёжно найти летсплей нужной игры;
- доступен ли проверяемый показатель популярности;
- можно ли устойчивым и допустимым способом получить текст;
- что происходит при отсутствии текста или аудио;
- как ограничить объём транскрипта, задержку и стоимость;
- как оценивать качество итогового заключения.

Если gate не пройден, дополнительная часть не должна реализовываться нестабильным обходным путём.

## 8. Последовательность разработки

Работа ведётся вертикальными инкрементами: каждый этап должен оставлять демонстрируемое и проверяемое состояние.

| Этап | Результат | Условие выхода |
|---|---|---|
| 0. Подготовка | Матрица требований, допущения, риски, минимальные проверки проекта и тестовое развёртывание | Проект воспроизводимо запускается из чистого checkout |
| 1. Один сквозной объект | Одна репрезентативная игра проходит путь от источника до карточки | Все обязательные поля проверены, повтор не создаёт дубль, результат виден публично |
| 2. Пакет и календарный цикл | Работают партии, переходы между источниками и новый день | Пройдены тесты первого/последующих запусков, смены даты, рестарта, частичного сбоя и пересечения запусков |
| 3. Отзывы и AI | Есть отдельные обновляемые резюме критиков и пользователей | Формат валидируется, evaluation set проходит зафиксированный порог |
| 4. Обязательный UI | Работают список, карточка, поиск, фильтр, сортировка и похожие игры | Пройден основной пользовательский E2E-сценарий |
| 5. Эксплуатационная готовность | Фоновая работа наблюдаема, сбои диагностируются | Подтверждён реальный плановый запуск, smoke-тест публичной версии успешен |
| 6. Дополнительная часть 2 | Мониторинг и принудительный запуск | Статусы правдивы, запуск не конфликтует с уже идущей работой |
| 7. Дополнительная часть 1 | Летсплей, текст и заключение | Feasibility gate пройден, качество и отказные сценарии проверены |
| 8. Финальная приёмка | Комплект результатов готов к передаче | Definition of Done выполнен, ссылки проверены извне, секретов нет |

После каждого инкремента должны оставаться:

- работающая версия;
- актуальные автоматические проверки;
- актуальная документация;
- небольшой осмысленный commit;
- evidence для закрытых требований.

## 9. Практики, критичные для задания

### 9.1. Идемпотентность и восстановление — Must

Почасовые, ручные и повторные запуски должны быть безопасными.

Необходимо доказать следующие инварианты:

- игра не дублируется при повторном обнаружении;
- платформенные данные не размножаются при обновлении;
- уже успешно сохранённые результаты не повреждаются при падении посередине партии;
- после рестарта не теряется дневной прогресс;
- неуспешную обработку можно повторить без повторной обработки всего набора;
- ошибка одной игры или необязательного обогащения не срывает весь прогон;
- пересекающиеся запуски не должны приводить к двойной обработке одной и той же работы;
- пустой или частично извлечённый ответ не должен молча затирать ранее корректные данные.

Методология не навязывает конкретную модель состояния, но реализация должна позволять отличить:

- успешное завершение;
- незавершённую попытку;
- частичный результат;
- ошибку;
- возможность безопасного повтора.

Также должно быть возможно понять, на какой стадии произошёл сбой и к какому запуску он относился.

### 9.2. Defensive scraping и качество данных — Must

Metacritic рассматривается как недоверенный и изменчивый внешний контракт.

Обязательны:

- явные таймауты;
- разумное ограничение частоты запросов;
- ограниченные повторы только для временных ошибок;
- различение HTTP-, сетевых, структурных и контентных ошибок;
- корректная обработка отсутствующих необязательных данных;
- строгая проверка обязательных данных на границе системы;
- сохранённые варианты страниц для тестов;
- заметный сигнал при существенной деградации полноты извлечения;
- возможность установить источник и время получения данных для диагностики.

Критический отказ parser contract должен быть заметен.

Молчаливое заполнение базы пустыми или неверно сопоставленными значениями хуже явной ошибки.

### 9.3. Календарная семантика — Must

Логика «раз в час», «сегодня не обрабатывал» и «каждый новый день начинаем заново» является самостоятельной бизнес-логикой.

Её следует тестировать с управляемым временем.

Обязательные сценарии:

- первый запуск дня;
- несколько последовательных запусков;
- исчерпание текущей страницы и переход дальше;
- переход через полночь в выбранной временной зоне;
- рестарт между запусками;
- падение на середине партии;
- повтор после ошибки;
- пересечение планового и ручного запусков.

### 9.4. Качество AI — Must

Отзывы и транскрипты считаются недоверенным внешним текстом, а ответ модели — вероятностным результатом.

Для AI-функций нужны:

- раздельные входы и результаты для критиков и пользователей;
- заранее определённый и валидируемый формат ответа;
- версия prompt, модели и значимых параметров;
- трассируемость результата до того набора входных данных, на котором он был построен;
- повторная генерация при существенном изменении входа или версии, а не безусловно при каждом запуске;
- контроль контекста, задержки и стоимости;
- корректная деградация при недоступности модели;
- защита от инструкций, содержащихся во внешнем тексте;
- безопасное отображение AI-текста;
- регрессионная оценка после изменения prompt или модели.

Трассируемость не означает обязательное хранение исходных отзывов в конкретной форме. Методология требует лишь возможности доказать, на основании каких входных данных был получен результат.

#### Рубрика AI-eval

Минимальная рубрика:

1. Резюме опирается только на предоставленные отзывы.
2. Положительные и отрицательные аспекты различимы.
3. Мнения критиков и пользователей не смешиваются.
4. Повторяющиеся важные темы отражены корректно.
5. Единичное мнение не выдаётся за общий консенсус.
6. При недостатке данных нет выдуманного заключения.
7. Формат, язык и длина соответствуют контракту.

До финальной оценки фиксируются:

- состав evaluation set;
- шкала оценки;
- baseline;
- минимальный проходной критерий.

Изменение prompt или модели должно сравниваться с baseline, а не оцениваться только субъективно.

### 9.5. Похожие игры — Must

Функция похожих игр должна иметь проверяемые свойства независимо от конкретного алгоритма.

Нужен небольшой вручную проверенный набор примеров.

Проверяется, что:

- игра не рекомендует саму себя;
- результаты берутся только из уже загруженной базы;
- при маленькой базе поведение остаётся корректным;
- после появления новых игр результат обновляется предсказуемо;
- изменение метода не ухудшает очевидные примеры незаметно.

### 9.6. Пользовательский сценарий — Must

Вместо большого количества изолированных UI-тестов достаточно короткого обязательного сквозного сценария:

> открыть список → найти игру по части названия → применить фильтр платформы → изменить сортировку → открыть карточку → проверить полные данные и оба резюме → перейти к похожей игре

Дополнительно следует проверить:

- пустую базу;
- отсутствие результатов поиска;
- игру без оценок;
- игру без отзывов;
- несколько платформ;
- длинные названия;
- недоступное изображение или видео.

### 9.7. Наблюдаемость — Must / Should

Полноценная realtime-панель относится к дополнительной части, но диагностируемость автономного фонового процесса обязательна.

**Must:**

- видно начало и завершение запуска;
- видно успешность или ошибку;
- видно количество обработанных и ошибочных элементов;
- известно время последнего успешного запуска;
- ошибку можно связать с конкретной игрой и конкретным запуском.

**Should:**

- структурированные события;
- correlation identifiers;
- длительности этапов;
- количество повторов;
- статистика AI-вызовов и расходов, если она доступна.

Если реализуется дополнительная realtime-панель, она должна показывать реальные данные процесса, а не имитировать прогресс на клиенте.

### 9.8. Безопасность и ответственная работа с источниками — Must / Should

**Must:**

- секреты не находятся в коде, логах и AI-истории;
- внешние HTML, отзывы и AI-тексты считаются недоверенными;
- публикуемая AI-история проверяется на секреты и персональные данные;
- административные действия не должны быть случайно доступны анонимному пользователю.

**Should:**

- автоматическая проверка репозитория на утечки секретов;
- проверка зависимостей на известные уязвимости;
- документирование ограничений внешних источников и правил их использования.

Лучше не передавать чувствительные данные модели изначально, чем пытаться очищать историю перед сдачей.

## 10. Стратегия тестирования

Цель тестирования — покрыть наиболее рискованные границы, а не добиться формальных 100% покрытия.

| Уровень | Что проверяется | Приоритет |
|---|---|---|
| Unit | Календарные правила, выбор следующих элементов, нормализация, валидация, сортировка и чистая логика | Must |
| Fixture / contract | Извлечение данных из сохранённых вариантов страниц Metacritic | Must |
| Integration | Сохранение и обновление, уникальность, повторный запуск, дневной прогресс | Must |
| Failure tests | Timeout, 403/429/5xx, недоступность AI, некорректный ответ модели, ошибка внутри партии | Must |
| Concurrency | Пересечение планового и ручного запусков, повторная доставка одной работы | Must |
| AI eval | Достоверность и стабильность двух видов резюме | Must |
| Similarity eval | Качество похожих игр на небольшом golden set | Must |
| E2E | Основной пользовательский путь от списка до похожей игры | Must |
| Deployment smoke | Публичная доступность, сохранение состояния и фактический фоновый запуск | Must |
| Live contract check | Контролируемая проверка актуального внешнего контракта | Should |

Основной CI не должен зависеть от живого Metacritic или платных AI-вызовов.

Live contract check следует выполнять отдельно и контролируемо.

## 11. Git, CI/CD и публичная поставка

Для тестового достаточно лёгкой, но последовательной инженерной дисциплины.

### Must

- небольшие логические commits;
- воспроизводимый запуск из чистого checkout;
- шаблон конфигурации без настоящих секретов;
- ранний деплой первого вертикального среза;
- финальный smoke-тест публичной версии;
- финальная проверка публичных ссылок из внешней неавторизованной сессии.

### Should

- форматирование;
- lint / type checks;
- автоматические тесты и build в CI;
- управляемые миграции при изменении схемы данных;
- smoke-тест после каждого значимого развёртывания.

Не требуется:

- сложная стратегия ветвления;
- тяжёлый обязательный code-review процесс;
- семантическое версионирование ради самого процесса;
- преждевременная автоматизация релиза.

История изменений должна быть понятной, но процесс не должен становиться самоцелью.

## 12. Документация и AI-артефакты

README должен позволить проверяющему за несколько минут понять:

- что реализовано из обязательной части;
- что реализовано из дополнительных частей;
- где находится публичный сервис;
- как запустить проект локально;
- как запустить проверки;
- как на уровне поведения работает почасовой и дневной цикл;
- какие внешние сервисы и AI-модели используются;
- какие допущения и ограничения приняты;
- как диагностировать последний запуск;
- как инициировать ручной запуск, если он реализован;
- где находится история взаимодействия с AI.

Дополнительно следует иметь:

- матрицу требований;
- журнал допущений и существенных решений;
- краткий реестр рисков;
- инструкции по диагностике типичных отказов;
- версии runtime-prompts;
- описание AI-eval;
- историю AI-assisted разработки.

Историю работы с AI следует сохранять с первого дня в исходном порядке и не реконструировать задним числом.

Перед публикацией архива выполняется проверка на:

- токены и API-ключи;
- пароли;
- персональные данные;
- лишние внутренние сведения.

Если часть истории пришлось удалить, это следует обозначить явно.

## 13. Definition of Done

Задание считается готовым к отправке, когда одновременно выполнены следующие условия.

### Функциональность

- Все обязательные строки матрицы требований имеют evidence.
- Продемонстрированы первый, последующий и новый дневной циклы.
- Повторное обнаружение обновляет игру без дублей.
- Корректно представлены несколько платформ и их оценки.
- Резюме критиков и пользователей разделены.
- Список, карточка, поиск, фильтр, сортировка и похожие игры прошли сквозную проверку.

### Надёжность

- Повторные и пересекающиеся запуски безопасны.
- Сбой одной игры или AI-вызова не разрушает всю партию.
- Ранее корректные данные не повреждаются частично извлечённым результатом.
- После рестарта сохраняется дневной прогресс.
- Parser contract проверен на сохранённых вариантах страниц.
- Существенная деградация извлечения заметна.

### AI-качество

- Evaluation set и рубрика зафиксированы.
- Резюме проходят минимальный критерий качества.
- Prompt и model version прослеживаются.
- AI-результат трассируется до использованного входа.
- Изменения AI-логики можно сравнить с baseline.

### Эксплуатация

- Публичный сервис доступен.
- В нём присутствуют реальные данные.
- Фактический почасовой запуск подтверждён логом или метрикой.
- Последний успешный запуск диагностируется.
- После перезапуска данные и дневной прогресс сохраняются.

### Поставка

- Проект воспроизводимо запускается из чистого checkout.
- README достаточен для запуска и оценки.
- В репозитории, логах и AI-архиве нет секретов.
- Проверены ссылка на репозиторий и ссылка на сервис.
- Подготовлена история AI-взаимодействий.
- Все публичные ссылки проверены из внешней сессии.

Дополнительная часть считается завершённой только при наличии:

- собственного критерия приёмки;
- обработки отказных сценариев;
- демонстрации в публичной версии.

Незавершённая bonus-функция не должна снижать качество обязательного контура.

## 15. Критерий достаточности

Для этого задания не нужен максималистский production-процесс.

Достаточный процесс должен:

1. однозначно описывать ожидаемое поведение;
2. рано снимать главные внешние риски;
3. поставлять систему сквозными рабочими срезами;
4. доказывать корректность дневной и повторной обработки;
5. отдельно измерять качество AI;
6. обеспечивать диагностируемость фоновой работы;
7. иметь публично проверяемый результат;
8. сохранять прозрачную историю AI-assisted разработки;
9. не тратить время на практики, не связанные с рисками или критериями приёмки.

Финальный результат должен выглядеть не как максимально сложная система, а как компактное, проверяемое и воспроизводимое инженерное решение, в котором каждое обязательное требование подтверждено конкретным evidence.
