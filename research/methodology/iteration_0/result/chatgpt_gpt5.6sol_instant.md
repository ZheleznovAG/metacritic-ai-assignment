Я бы рассматривал это задание не как «сделать парсер + прикрутить LLM», а как небольшой **production-like data/AI service**, где проверяется способность организовать надежный конвейер: регулярно получать внешние данные, обогащать их AI-обработкой, сохранять согласованно и предоставлять через веб-интерфейс.

При этом ниже я намеренно **не проектирую архитектуру и не выбираю конкретный стек**, а определяю инженерный процесс и практики, которые нужны для качественного выполнения.

### 1. Сначала — декомпозиция требований и критерии приемки

В задании есть несколько разных по природе контуров работы. Сервис должен раз в час выбирать 20 еще не обработанных сегодня игр, а с наступлением нового дня начинать обход заново; существующие игры при этом должны обновляться. 

Поэтому до реализации стоит превратить текст задания в **явные acceptance criteria**. Отдельно зафиксировать:

* получение списка игр;
* получение полной информации об игре;
* поддержку нескольких платформ и рейтингов;
* обработку отзывов критиков;
* обработку отзывов пользователей;
* AI-суммаризацию;
* подбор похожих игр;
* поиск/фильтрацию/сортировку в UI;
* периодический запуск;
* повторную обработку и обновление данных;
* ежедневный reset логики обхода;
* обработку ошибок и частично полученных данных.

Особенно важно формализовать неоднозначности. Например, «не обрабатывал сегодня» и одновременно «информация может обновляться при повторных обходах» требуют осознанно определить семантику повторной обработки. Само задание допускает обновление резюме отзывов. 

Хорошая практика здесь — сделать короткий `REQUIREMENTS.md` или соответствующий раздел README с таблицей **требование → способ проверки**.

### 2. Разработка должна идти вертикальными срезами

Не стоит сначала писать весь scraping, затем всю AI-часть, затем UI.

Лучше двигаться через работающие end-to-end инкременты:

**Первый срез:** одна игра проходит полный минимальный путь от внешнего источника до базы и отображения.

**Второй:** 20 игр и корректное повторное сохранение.

**Третий:** расписание и дневной цикл.

**Четвертый:** отзывы и AI-обработка.

**Пятый:** похожие игры.

**Шестой:** полноценный пользовательский интерфейс.

После этого — дополнительные части.

Так намного раньше обнаруживаются проблемы интеграции, чем при разработке компонентов изолированно.

### 3. Для сбора данных нужна практика defensive scraping

Metacritic здесь является внешней зависимостью, которую сервис не контролирует. Причем требуется извлекать не только список, но название, обложку, платформенные оценки, разработчика, описание и видео. 

Поэтому scraping следует воспринимать как ненадежный I/O.

Нужны практики:

* timeout;
* ограниченные retries с backoff;
* rate limiting;
* нормальный User-Agent;
* обработка HTTP-ошибок;
* tolerance к отсутствующим полям;
* валидация распарсенных данных;
* структурированные ошибки парсинга;
* фикстуры HTML для тестов;
* обнаружение изменения структуры страницы;
* логирование URL и стадии, на которой произошла ошибка.

Особенно важно **не связывать тесты парсера с живым Metacritic**. Набор сохраненных HTML fixtures позволяет воспроизводимо тестировать parser независимо от доступности сайта.

### 4. Ключевая практика — идемпотентная обработка

Это, вероятно, один из важнейших инженерных аспектов задания.

Сервис должен и добавлять новые игры, и обновлять уже существующие. 

Следовательно, повторный запуск одной и той же работы не должен:

* создавать дубликаты;
* портить существующие данные;
* дублировать платформы;
* запускать ненужную дорогую AI-обработку;
* нарушать состояние дневного обхода.

Полезный критерий:

> один job можно безопасно выполнить повторно после timeout/crash.

Для этого нужны стабильная идентификация сущностей, upsert-семантика, ограничения уникальности и явное состояние обработки.

### 5. Pipeline должен иметь наблюдаемое состояние

Здесь недостаточно бинарного `processed=true`.

Обработка игры фактически многостадийна: обнаружение → получение деталей → отзывы → AI → похожие игры → завершение.

Поэтому инженерная практика — моделировать **состояние обработки**, чтобы после ошибки было понятно:

* какая игра обрабатывалась;
* какая стадия завершилась;
* где произошла ошибка;
* можно ли повторить только неуспешную часть;
* когда была последняя успешная обработка.

Это становится особенно важным для дополнительного требования о real-time мониторинге статусов воркеров и количества обработанных записей. 

Даже если дополнительную часть не делать, такая модель сильно улучшает надежность основной.

### 6. AI-часть требует отдельной дисциплины

Суммаризация отзывов — не просто один вызов модели. По условию нужны **два разных результата**: по критикам и по пользователям. 

Нужны практики AI engineering:

* версионирование prompts;
* фиксированный формат результата;
* ограничение размера входного контекста;
* стратегия работы с большим числом отзывов;
* защита от prompt injection внутри собираемого текста;
* retries/timeouts;
* логирование latency и ошибок;
* контроль стоимости вызовов;
* возможность повторной генерации;
* сохранение версии prompt/model рядом с результатом либо в metadata.

Кроме обычных unit-тестов здесь нужен небольшой **evaluation dataset**: несколько заранее выбранных игр/наборов отзывов и критерии, по которым вручную проверяется качество summary.

Цель не в том, чтобы доказать математически, что summary «правильное», а в том, чтобы изменение prompt/model не ухудшало результат незаметно.

### 7. Similar games тоже следует оценивать как ML/AI-функцию

Задание требует подбирать похожие игры **из уже находящихся в базе**. 

Какой бы метод реализации ни был выбран позднее, процесс разработки должен включать evaluation.

Нужен маленький golden set вида:

`игра → несколько разумно похожих игр`

и проверки:

* действительно ли рекомендации похожи;
* не рекомендует ли система саму игру;
* корректно ли работает при маленькой базе;
* что происходит после добавления новых игр;
* насколько детерминирован результат.

Иначе функция может технически работать, но выдавать бессмысленные рекомендации.

### 8. Планировщик необходимо тестировать отдельно от реального времени

Логика «раз в час / следующие 20 / новый день начинаем сначала» — самостоятельная бизнес-логика, а не просто настройка cron. 

Поэтому время желательно сделать управляемой зависимостью в тестах.

Нужны сценарии:

* первый запуск дня;
* второй запуск;
* несколько запусков подряд;
* переход 23:xx → следующий день;
* restart приложения;
* падение посередине batch;
* ручной повторный запуск;
* два запуска одновременно.

Особенно полезен тест на **concurrency**, чтобы два worker/job не обработали один batch одновременно.

### 9. Нужна трехуровневая стратегия тестирования

Для такого тестового задания оптимален не максимальный coverage, а правильно выбранные тесты.

**Unit tests** — parsing, нормализация данных, выбор следующих игр, ranking/similarity, преобразования AI-output.

**Integration tests** — база данных, upsert, ограничения уникальности, pipeline нескольких стадий, API.

**Несколько end-to-end smoke tests** — загрузить подготовленные данные → обработать → открыть список → найти игру → открыть карточку → проверить платформы/summary/similar games.

Живой Metacritic и реальные AI API лучше оставить для небольшого количества smoke/integration проверок, а основную тестовую базу сделать воспроизводимой.

### 10. Наблюдаемость — часть решения, а не украшение

Минимально нужны structured logs с идентификаторами `run/job/game`, чтобы можно было проследить одну обработку от начала до конца.

Стоит измерять:

* продолжительность run;
* число discovered/processed/updated/failed;
* длительность scraping;
* длительность AI;
* число AI-вызовов;
* retries;
* последнюю успешную обработку.

Это одновременно облегчает разработку и естественным образом подготавливает основу под дополнительный monitoring UI.

### 11. CI/CD должен появиться достаточно рано

Поскольку результатом должны быть **репозиторий и работающий развернутый сервис**, deployment — часть задания, а не действие после окончания разработки. 

Минимальный инженерный цикл:

`изменение → lint/format → tests → build → deploy → smoke test`

Стоит сделать staging/production-like deployment уже после первого вертикального среза. Тогда проблемы окружения, migrations, secrets и фоновых процессов не обнаружатся за час до сдачи.

Секреты и API keys — только через environment/secrets management, никогда в repository.

### 12. Git-процесс должен показывать ход инженерной работы

Для тестового задания история репозитория сама является частью демонстрации качества.

Лучше делать небольшие содержательные commits:

`bootstrap service`
`add game ingestion`
`make ingestion idempotent`
`add review summarization`
`add scheduler`
`add similar games`
`add game search and filters`

а не один огромный `final`.

Полезны короткие feature branches или хотя бы логически чистые commits, обязательный проход CI перед merge и отсутствие generated/secrets файлов в истории.

Это особенно актуально потому, что заказчик отдельно просит предоставить всю переписку с нейросетью.  То есть AI-assisted development здесь явно разрешен, но по результату должно быть видно, что решения проверялись инженером, а не просто генерировались.

### 13. Definition of Done стоит определить заранее

Для каждой функциональности «готово» должно означать не только «код написан».

Например:

**implemented → tested → observable → documented → deployed → manually verified**

А для всего задания финальный DoD примерно такой: обязательные сценарии проходят; повторный запуск безопасен; ошибки внешних сервисов не ломают весь процесс; deployment воспроизводим; migrations работают; UI доступен; README позволяет запустить проект с нуля; есть понятное описание ограничений; CI зеленый; нет секретов в Git; production smoke test проходит.

Дополнительные части — YouTube/транскрипция и real-time monitoring — логично брать **только после стабилизации обязательного контура**. Они существенно расширяют поверхность отказов, тогда как обязательная часть уже сама по себе проверяет scraping, persistence, scheduling, AI, similarity и web development. Требования дополнительных частей описаны отдельно и действительно не являются prerequisite основной функциональности. 

В итоге оптимальный процесс здесь выглядит как **requirements → acceptance criteria → вертикальный MVP → automated tests → reliable/idempotent processing → AI evaluation → observability → ранний deployment → hardening → дополнительные функции → финальный acceptance run**.

Следующим полезным шагом я бы сделал **план реализации по этапам с Definition of Done для каждого этапа и приоритетами P0/P1/P2**, всё ещё без выбора архитектуры и конкретных технологий.
