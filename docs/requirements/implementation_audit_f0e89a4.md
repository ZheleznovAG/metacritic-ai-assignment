### A04 · P2 · GitHub CI и VDS проверяют разные бинарные образы

**Тип:** подтверждённый пробел цепочки выпуска.
**Связи:** `NFR-06`, `PUB-01`, `REL-01`, воспроизводимость.

Для одного source SHA `37b44fb`:

- CI проверил `sha256:0b844d01d1ae61b83cf4d4a93e533044f7132f85ed912d95fb39c51550639e2e`.
- На VDS запущен `sha256:1a066e03c051b845429db8e36a2155dbc8ac80a91d40d723b47492460f67808d`.

[Workflow](../../.github/workflows/ci.yml) собирает и проверяет образ, затем удаляет
окружение; готовый runtime artifact не передаётся в deployment.
[Runbook](../../deploy/README.md) предлагает отдельный `docker build` перед `docker save`.
Разные image IDs сами по себе не доказывают различие поведения: они возможны при
повторной сборке. Но hosted CI не подтверждает именно тот бинарный artifact,
который работает на сервере. Identity checks подтверждают доставку локально выбранного образа.

**Закрытие:** один раз собирать и проверять release image, сохранять/публиковать его
как artifact с digest и разворачивать именно его. Ручной разрешённый deploy при этом
может остаться ручным. Runtime/config/lock между deployed source и HEAD сейчас совпадают.

### A05 · P2 · Scheduler не восстанавливает run после сбоя между записью intent и lease

**Тип:** новый воспроизведённый counterexample.
**Связи:** `HRD-02`, `RUN-01`, `NFR-01`, `NFR-05`.

[scheduler.py](../../app/processing/scheduler.py) сначала создаёт ProcessingRun,
затем получает lease. Любая существующая запись trigger key немедленно приводит
к `skipped_duplicate`, независимо от status/owner/expiry.

В изолированной PostgreSQL-проверке сбой перед acquire_lease оставил `queued`.
Повтор через минуту не вызвал gateway и вернул `skipped_duplicate`. В следующем
часу новая работа успешно прошла, но исходный run остался `queued`, `ended_at=null`.
Поэтому здесь доказаны пропуск восстановления в текущем слоте и неверное бессрочное
состояние run; не доказана потеря всего дневного прогресса.

**Закрытие:** явное восстановление прерванных run/intent с учётом ownership,
атомарных границ и запрета повторной подтверждённой работы. Проверять сбой после
создания run, после lease, после core commit и перед финальным закрытием run.

### A06 · P2 · Настройка Groq timeout не влияет на реальный запрос

**Тип:** новый воспроизведённый дефект.
**Связи:** `HRD-04`, `NFR-04`, ограничение provider time.

[run_worker.py](../../app/reviews/management/commands/run_worker.py) читает
`GROQ_API_TIMEOUT_SECONDS` и создаёт `httpx.Client(timeout=timeout)`.
Но [groq_adapter.py](../../app/summaries/groq_adapter.py) передаёт в `client.post`
явное `timeout=DEFAULT_TIMEOUT_SECONDS`, равное 180.

MockTransport подтвердил: клиент с timeout 0.025 отправляет запрос с
connect/read/write/pool timeout 180. Настройка оператора игнорируется.

**Закрытие:** один источник настройки, проверка допустимого диапазона и тест на
эффективные timeout extensions реального adapter request.

### A07 · P2 · HTTP timeout не ограничивает полное время и размер ответа источника

**Тип:** подтверждённая граница hardening, `HRD-01/HRD-05` ещё не закрыты.
**Связи:** `NFR-04`, `R-EXT-01`, resource bounds.

[gateway.py](../../app/metacritic/gateway.py) использует обычный `client.get`,
после которого весь body уже загружен в память. Ограничения размера нет.
Изолированный поток из 256 блоков принят целиком: 8 388 608 bytes, outcome succeeded
на уровне HTTP adapter. Это проверка загрузки до parser, не утверждение о валидности HTML.

Число 15 в HTTPX timeout означает, в частности, максимально допустимое ожидание
очередного блока, а не максимальную длительность всего ответа.
Медленно поступающий поток может пережить этот интервал многократно.
[Документация HTTPX](https://www.python-httpx.org/advanced/timeouts/).

**Закрытие:** streaming с лимитом полученных/декодированных bytes, общий deadline,
классифицированный отказ без записи неполных данных; отдельные bounded retry policies.
Настоящий длительный slow-stream в этом аудите не запускался.

## Что в CI сделано правильно

- Выполняются реальные проверки, а не только lint: Ruff, strict mypy, Django system
  checks, migration drift, static build, PostgreSQL tests и Chromium E2E.
- Проверки одни и те же локально и в CI через `scripts/check.py`.
- Используется PostgreSQL 16, не SQLite; тесты permissions выполняют реальные
  разрешённые и запрещённые запросы.
- Детерминированный runtime test-контур находится во внутренней Docker-сети,
  Metacritic/Groq заменены fixtures/fakes; браузерное скачивание происходит на build stage.
- Python/uv/PostgreSQL/Caddy и checkout action закреплены версиями/digest/SHA,
  зависимости устанавливаются с `uv sync --locked`.
- Runtime проверяется с read-only filesystem, без сети для tokenizer smoke;
  HTTP/CSS smoke выполняется через настоящий Caddy.
- CI имеет `contents: read`, checkout не сохраняет credentials, production/SSH/Groq
  secrets не нужны. CI самостоятельно не разворачивает VDS — это корректная текущая граница.
- Последняя ошибка CI действительно была обнаружена whitespace check и исправлена.

Оставшиеся пробелы CI: production override проходит только `config --quiet`,
его production provisioning path не запускается отдельным CI-сценарием; проверка
обновления старой БД/restore отсутствует; browser traces/screenshots/container logs
не выгружаются как artifacts при падении; generic secret scan в workflow не включён.
Они важнее косметической оптимизации времени pipeline, которое сейчас около 2.5 минут.

## Что в развёртывании сделано правильно

PostgreSQL не публикуется наружу; web доступен только во внутренней сети;
у web UID/GID 65532 и read-only rootfs; credentials передаются по ролям;
`.env.app` имеет mode 0600; image identity и checksums проверяются; данные живут
в отдельных именованных volumes; логи основных services ограничены 3 × 5 MiB;
Docker включён в автозапуск, основные services имеют `unless-stopped`.

Цепочка `db_setup → migrate → web → caddy` использует
`service_completed_successfully`/`service_healthy` по назначению.
[Семантика Compose](https://docs.docker.com/compose/how-tos/startup-order/).
Exited db_setup/migrate не означают поломку: оба имеют ExitCode 0. Унаследованная
web healthcheck даёт им ненужный unhealthy status; для one-shot services её лучше отключить.

Healthcheck и `restart: unless-stopped` сами по себе не подтверждают recovery:
restart policy реагирует на завершение контейнера/рестарт daemon, а не служит
детектором зависшей бизнес-обработки.
[Семантика Docker restart policies](https://docs.docker.com/engine/containers/start-containers-automatically/).

Дополнительный пробел runbook: Caddyfile bind-mounted, `admin off`, а изменение
содержимого Caddyfile не сопровождается явным reload/recreate Caddy. Обновление
proxy-конфигурации следует отдельно применять и проверять. Сейчас расхождения
проверенного файла с checkout нет; runtime reload-контрпример на VDS не запускался.

## Прогресс и направление разработки

Сильные стороны реализации — выбранный модульный монолит, явные границы
адаптеров, immutable review snapshots, provenance, leases/fencing, durable attempts,
контроль token budget и отложенная AI-очередь. Это соответствует рискам задания.
Дальнейшее дробление на микросервисы или добавление Redis/Celery/SPA сейчас
не подтверждено потребностями.

Frozen evaluation и сравнение similarity policies лучше интуитивной настройки:
есть 14 synthetic cases, thresholds и invariants. Однако результат 1.0 на этом
oracle не означает универсального качества рекомендаций. У 18 из 39 публичных
игр genres отсутствуют; честный empty state корректен, но покрытие следует измерять
на реальном каталоге. Для AI два успешных live calls доказывают интеграцию,
но не устойчивую пропускную способность и итоговую репрезентативность.

В `quota.py` приложение ограничивает себя 200 000 tokens/day и учитывает полную
reservation. Две текущие VDS попытки резервировали 2 741 и 2 655 tokens.
Если условно все вызовы стоили бы столько же, лимит дал бы около 74 summaries/day
(около 37 игр с двумя model summaries). Это иллюстрация риска, не измеренная capacity:
cache, insufficient_data, изменение отзывов, retries и реальный corpus меняют поток.
При максимальной reservation 6 800 хватает лишь на 29 попыток в rolling day.
Поэтому arrivals/cache/completions/backlog/oldest age в `HRD-04/PUB-02` — центральная
проверка реализуемости, а не необязательная метрика.

По исходной таблице оценок после G4 остаются **62 инженерных часа**:
35 hardening, 10 public validation, 1 решение о Bonus и 16 delivery.
Это сумма существующих baseline estimates, не новый прогноз и не оценка фактически
оставшегося времени. Резерв, ожидание DNS/расписания и найденные исправления в неё
дополнительно не включались. Процент готовности по числу документов вводил бы в заблуждение.

Предлагаемый порядок следующих циклов:

1. `HRD-02`: восстановление run/intent и сбои на commit boundaries, начиная с A05.
2. `HRD-01/03/04/05`: HTTP bounds, concurrency, эффективные provider timeouts,
   AI capacity, диагностика, storage и query scaling; по одной задаче за цикл.
3. `HRD-06`: совместный suite и честный G5 review; закрепить release artifact/checks.
4. `PUB-01`: supervised scheduler/worker, HTTPS и воспроизводимый deploy.
5. `PUB-02/03`: два окна, reboot, изолированный restore, внешняя проверка,
   измерение скорости накопления и разгрузки очередей.
6. После G6 — решение Bonus scope и комплект сдачи. Архив переписки, доступ к
   репозиторию и финальная сверка публичной версии остаются обязательными delivery-задачами.

## Пределы аудита

Четыре counterexamples выполнены в disposable PostgreSQL checks database с
fakes/MockTransport. Их PASS означает, что нежелательное поведение воспроизведено,
а не что приложение исправлено. Они проверяли A05, A06, A07 и A08; результаты
описаны в соответствующих разделах. Их не добавляли в application suite или CI.

Production SQL выполнялся через web role с `default_transaction_read_only=on`;
SSH использовал существующую identity и StrictHostKeyChecking. Проверка GitHub
rulesets ограничена ответом HTTP 403.

Production data/config/services во время аудита не изменялись. Миграции,
restart/reboot, restore, deployment, ingestion/AI-provider вызовы и платные
операции не выполнялись. Браузер загружал обычные публичные страницы и изображения.
Проверка секретов ограничена точным поиском настроенных значений в tracked-файлах;
полный generic/history scan не выполнялся.

Этот отчёт фиксирует состояние указанного коммита и датированного VDS-снимка.
При последующей разработке нужно воспроизвести относящееся к задаче замечание,
исправить причину и добавить проверку правильного поведения. Наблюдения о VDS,
очередях, CI и доступности GitHub могут измениться после даты аудита.
Сохранение отчёта не означает закрытия перечисленных замечаний или новых gates.
